前言

理解这些论文时，最值得抓住以下几条演进关系，跨论文归纳：

技术支线 问题如何变化
Firmadyne → FirmAE 从“建立批量执行流程”推进到“修复大量常见环境失败”。
ECMO / FirmGuide 从用户态服务转向原 kernel：前者移植驱动来利用已有仿真外设，后者生成外设模型来适配目标内核。
FirmSolo → FirmDiff / Pandawan 从“原模块能够加载”推进到“结构兼容修复、用户态与模块共同运行及测量”。
Greenhouse → FIRMWELL / Firmenstein 从围绕目标服务消除障碍，推进到用户态依赖恢复和 API 语义驱动的干预；这里表示问题承接。
FIRM-AFL → EQUAFL 从混合 system/user-mode 执行，推进到观察环境后尽量减少 system-mode 参与。
Penguin / FirmCure / FirmPilot 分别探索目标配置化修复、Agent 自适应修复，以及带执行证据的修改验收。

Firmadyne 建立执行基础，FirmAE 修复常见失败，Greenhouse 缩小恢复范围，Firmenstein 根据 API 语义诊断并合成干预。

Linux 固件仿真与重托管的核心工作

时间、论文/系统 重托管对象 基于什么、与前作的关系 此前具体卡在哪里 怎样解决
2016，NDSS：Firmadyne 原固件用户态＋替换内核的全系统环境 QEMU＋可插桩 Linux kernel，是后续 FirmAE 的直接基础 固件依赖专有硬件、启动配置和网络环境，难以脱离设备批量动态分析 提取 rootfs，使用 QEMU 支持的替代内核；补 NVRAM 接口，观测并推断网络配置，再接入动态检测。原文 §II、Fig.1
2016，AsiaCCS：Costin 等，Automated Dynamic Firmware Analysis at Scale 主要面向固件 Web 接口 通用同架构 Linux＋QEMU＋chroot；与 Firmadyne 是不同论文 大规模固件静态分析之后，仍缺少可实际访问和扫描的 Web 服务 在通用同架构 Linux 环境内 chroot 运行原用户态，修复文件系统并启动服务。不能把该方案统一理解为 QEMU-user。预印本 §I-A、§II-D(c/d)
2019，eCrime：Honware 固件服务与高交互蜜罐 QEMU＋预构建定制内核；针对已有固件仿真的联网、服务运行问题 模拟协议的蜜罐不够真实，购买大量真实设备又难扩展 从固件构建运行环境，适配 NVRAM、网络、信号等，并记录真实攻击交互。主要目标是攻击观测。原文 §III、Fig.1
2020，ACSAC：FirmAE 全系统环境中的用户态服务 直接扩展 Firmadyne Firmadyne 的执行流程具备了，但大量固件仍因启动、网络、NVRAM 和接口差异失败 总结五类失败，加入 boot/network/NVRAM/kernel/other arbitration，以启发式适配提高可运行性。原文 §3–4
2021，CCS：ECMO 原 Linux kernel 主体 LuaQEMU＋QEMU 已有外设及对应驱动；改变替换整个内核的路线 替换内核后无法研究原内核；保留原内核又会因 QEMU 不支持目标外设而无法启动 向目标内核注入驱动并重定向初始化/调用指针，让原内核使用 QEMU 支持的外设。原内核主体保留，但执行路径存在修改。原文 §3.2、§4.2–4.4
2021，ASE：FirmGuide 原 Linux kernel QEMU＋LLVM/KLEE；与 ECMO 是并行问题路线 为每种 SoC 手工实现外设模型成本高，通用 QEMU 又无法启动原内核 离线从内核子系统和驱动源码提取模型；在线根据目标 kernel/DTB 组合外设与 QEMU machine。离线需要源码，不等于每个目标都需要源码。原文 §III–V、Fig.4
2023，USENIX Security：FirmSolo 原厂二进制 kernel modules 自建 K.C.R.E.；下游集成、扩展 Firmadyne 和 TriforceAFL 通用替代内核与原 .ko 的版本、符号、配置和结构布局不匹配，模块无法加载 从模块元数据反推内核配置，重建兼容内核；结合加载错误继续校正配置与布局。原文 §3–4
2023，USENIX Security：Greenhouse Linux 用户态单服务 QEMU-user＋迭代监控/干预框架；可利用 FirmAE 部分启动信息 为分析一个服务恢复整个设备，容易被无关硬件依赖阻断 围绕目标服务反复发现 roadblocks，补文件、配置、NVRAM、网络等，必要时 binary patch；以 Execute、Connect、Interact 等阶段检查进展。原文 §4–6；限制 §8
2024，BAR：FirmDiff 原模块与重建内核的结构兼容性 直接使用 FirmSolo＋Ghidriff/Ghidra FirmSolo 仍可能因厂商修改结构体布局而失败，仅恢复 .config 不充分 对原模块与重编译对应模块进行 binary diff，提取成员偏移差异，辅助分析者修正配置或结构布局；修复包含人工步骤。原文 §IV、§VI-D
2024，USENIX Security：Pandawan 用户态＋原内核模块 FirmSolo＋PANDA/PyPANDA，并利用 FirmAE 基础 能加载模块不代表用户态服务也能完整运行；不同系统的“成功”定义难比较 Kernel Augmentation 补用户态所需功能；用 FICD 确定初始化测量参考点，联合观察用户程序、模块及执行覆盖。原文 §3–4
2025，BAR：Penguin 目标定制的全系统环境 PANDA/PyPANDA＋Firmadyne/FirmAE 部分分析组件 通用启发式写死在代码中，难适配新设备，也难解释和复现修改 将文件系统、NVRAM、网络等变换表示为目标配置；支持自动生成、动态插件、人工迭代和配置最小化。原文 §III–IV、Table I
2026，NDSS：FIRMWELL 目标服务及其用户态依赖进程 container＋QEMU-user 多进程环境；有 QEMU-system 兼容性后备 init 未完成会遗漏配置、IPC 和后台进程；当前服务的错误可能来自另一进程 先恢复初始化与依赖，定位 blocking process，追溯缺失资源的根因，再创建、推断或修复资源。原文 §III–IV
2026-06，预印本：FirmCure 全系统 Linux 环境 CrewAI＋QEMU＋近似匹配的替代内核；直接 FirmAE fork 未核实 固定规则难处理异构启动依赖、硬件探测阻塞和运行期故障 分阶段进行依赖识别、最小启动脚本生成、配置反思修复，再由 GDB、文件和网络专家 Agent 干预。预印本 §IV–V
2026-07，预印本：FirmPilot 全系统环境与网络服务 QEMU＋多 Agent 恢复框架；采用 FirmAE 兼容默认值，不据此认定代码继承 启动、持久配置和网络依赖耦合；Agent 任意修改难审计 Agent 输出带证据的 typed artifact deltas，通过重执行和固定 probes 验收修改。预印本 §IV–V
2026，USENIX Security：Firmenstein Linux 服务级环境、跨程序依赖 Joern CPG＋LangChain＋Qiling/LibAFL-QEMU；FirmAE、Greenhouse、Penguin 是比较对象 固定 stub/patch 缺乏 API 语义，复杂依赖难处理，干预还可能破坏程序状态 构建 API Dependency Graph，跨程序诊断 roadblocks；合成 intervention code，并通过 IIB 支持原生执行与干预逻辑交错调用。原文 §3–4、Fig.4/6

以Fuzzing为目标，但对仿真执行机制做出贡献的相关工作

时间、系统 基于什么 解决什么问题 怎样解决
2019，USENIX Security：FIRM-AFL Firmadyne＋QEMU-system/user＋AFL 全系统提供了环境，但每轮测试执行成本高 Augmented Process Emulation：尽量在用户态执行，环境相关操作由系统态处理，配合内存同步和 snapshot。依赖固件先能运行。原文 §3–4
2021，IEEE Access：FIRM-COV 优化 process emulation 的灰盒框架；确切代码继承未核实 仿真稳定性、输入结构和测试调度影响覆盖 优化进程仿真，结合字典生成与协同调度。本轮该项为摘要级证据。出版方摘要
2022，ISSTA：EQUAFL Firmadyne 环境＋增强 QEMU-user；针对 FIRM-AFL 的混合执行开销 频繁依赖 system-mode 仍然昂贵，直接 user-mode 又缺环境 先在全系统中 observe，再迁移环境，在增强 user-mode 中 replay 网络和资源行为。原文 Fig.1、§4
2023，CMC：AEMA FIRM-AFL 式混合执行＋FirmAE arbitration 思想 主流架构的环境失败，以及其他架构的测试接入 主流架构采用 arbitrated process emulation，其他架构接入不同 emulator；另结合 concolic 输入生成。实验平台异构，不能全部归为 Linux。原文 §3.1–3.2
2025，IEEE S&P：HouseFuzz 直接基于 Greenhouse 仅看目标进程会遗漏协作进程反馈，协议 token 依赖又阻碍有效输入 将协作进程作为服务整体，增加覆盖、异常和测试完成检测，并用 Token Dependency Graph 指导输入。原文 §5–7

其他的仿真路线

时间、系统 基础与解决方式 与 Linux 主线的适用差异
2014，Avatar S2E/QEMU＋实物外设转发，协调模拟器与硬件 运行时依赖设备；是硬件协同分析基础设施。原文 §III
2015，SURROGATES QEMU＋FPGA/PCIe 硬件桥，降低外设转发延迟 包含 Linux 实验，但仍需真实设备。原文 §4–5
2018，Avatar² Avatar 的全面重设计，统一多 target 编排与状态转移 通用分析编排平台，不直接解决大批 Linux 固件的服务恢复。原文 §III–IV
2019，PRETENDER 基于 Avatar²，记录真机 MMIO/中断并学习外设模型 记录阶段需要设备和充分交互覆盖。原文 §3
2020，P²IM QEMU＋自动寄存器接口分类与响应探索 MCU 裸机/轻量 OS，主要恢复 MMIO 与中断接口。原文 §3–4
2020，HALucinator angr 识别 HAL，Avatar² 控制 QEMU，以高层 handler 替换 HAL 依赖 HAL 知识；抽象边界是函数接口。原文 §3–4
2021，µEmu S2E/QEMU，以 invalid-state 反馈推断外设响应 MCU/轻量 OS；不恢复 Linux rootfs、NVRAM 和服务依赖。原文 §4
2021，Jetset QEMU＋angr＋Z3，为到达目标位置合成外设响应 跨 Linux、RTOS、bootloader；目标可达不等于完整设备恢复。原文 §5–6、Table 1
2022，Fuzzware Unicorn＋angr＋AFL，局部 DSE 推断 MMIO 中真正影响执行的位 ARM Cortex-M；重点是减少无效 Fuzzing 输入自由度。原文 §4–5
2025，GDMA 扩展 Fuzzware，利用迭代类型推断恢复 DMA 配置，复用 DICE 部分机制 ARM MCU 的 DMA 输入恢复，不代表 Linux DMA driver 环境已解决。原文 §5、§8
2025，Pemu 集成 Fuzzware、Hoedur、SEmu，通过虚拟网络封装协议有效输入 面向裸机/轻量 OS 网络栈，区别于 Linux socket 服务。原文 §4.3
2026，Khost 扩展 KVM，降低 MCU 重托管执行开销 被测对象是 MCU；宿主使用 Linux 不意味着目标是 Linux 固件。本轮为摘要级证据。官方页面
