前言

动态分析的发展，可以沿着一条主线理解：让目标可测试 → 产生有效输入 → 探索路径和状态 → 观察真正的故障 → 形成可重放的漏洞证据。 吞吐优化、状态建模、动态污点、符号执行和 LLM，分别在补这条链上的不同缺口。

各分支一直并行发展：黑盒测试适合无法插桩的设备，灰盒测试利用内部反馈，符号执行帮助处理约束，重托管提供执行条件。

Linux-based IoT Firmware 动态分析技术发展脉络与研究现状

文献时间范围：早期基础工作至2026年10月31日；本轮核查日期：2026年11月3日。以Linux-based IoT Firmware自动漏洞发现为核心，将物理设备黑盒、通用协议方法、MCU/RTOS分别标注。本文是问题驱动的代表性调研，不是穷尽所有数据库的系统综述，也不是系统效果排名。

本轮采用关键词检索、种子论文参考文献回溯、针对性后续工作追踪；没有声称遍历Google Scholar或Semantic Scholar的全部cited-by。重要机制优先核查官方/作者全文，摘要级与预印本分别标记。所有用户阅读状态保持“未确认”；全文可访问、方法局部核查、完成全文精读和实际复现是不同状态。本轮没有部署系统或独立重放PoC。

1. 先看清动态分析研究的完整链条

动态漏洞分析的目标是让输入在具体执行或明确的执行模型中触发可判断的安全后果。研究至少沿六个维度并行推进：

维度 核心问题 典型研究切入点
执行条件 目标能运行，且所需环境成立吗？ Firmadyne、FirmAE、Greenhouse、FIRMWELL、Firmenstein
输入与入口 请求能被接受，是否覆盖隐藏接口/字段？ FirmFuzz、IoTFuzzer、Snipuzz、IoTScope、EAGLEYE、PANGOLIN
探索反馈 测试下一步该改什么、向哪里走？ coverage、响应代理、distance、状态转移、动态污点
状态与边界 必要前置请求、协作进程、持久状态是否保留？ SIoTFuzzer、FirmHunter、HouseFuzz、STAFF、Camveil
漏洞oracle 怎样分辨崩溃、无响应、命令副作用和逻辑违约？ WYCINWYC、FirmFuzz、CGIFuzz、mGPTFuzz、HouseFuzz
验证与评测 结果能重放吗，改进来自算法还是环境？ FirmRec、Bond、FirmAgent、IoTFuzzBench、LFwC、SoK2024

这些维度是本轮跨论文归纳。黑盒/灰盒/符号执行不是按年份互相替换的代际：黑盒应对无法内部插桩的设备，灰盒利用低成本运行反馈，concolic/symbolic execution用约束探索或验证路径。是否拥有源码是另一条轴；二进制也能符号执行，但环境模型和指令支持仍是前提。S2E §3–5、Driller §3–4。

6. 把时间表串起来：一路究竟解决了哪些障碍

下列阶段是教学上的问题组织，时间相互重叠；后来的方法通常只推进部分维度。不能理解为“黑盒被灰盒替代，灰盒再被LLM替代”。

6.1 从测试程序到测试设备：首先缺的是可执行条件与输入通道

KLEE/S2E提供路径探索能力，但未知设备的外设、kernel、配置和启动依赖不会因此自动消失。Firmadyne/FirmAE逐步构建批量执行条件；另一路IoTFuzzer利用companion App已经具备的协议和加密逻辑，把变异输入送入真实设备。两条路线解决的是不同约束：一条获得可控执行环境，一条保留真实设备并复用合法通信入口。Firmadyne §II、FirmAE §3–4、IoTFuzzer §II–III。

新增能力是“可以持续向目标提交测试并观察”；尚未解决的是测试吞吐、深层有效输入与状态前置条件。

6.2 从能运行到能高频测试：执行成本成为可分离的研究问题

FIRM-AFL把用户态快速执行和system-mode环境支持结合；EQUAFL进一步将初始化环境先observe，再尽量迁移到增强user-mode replay，减少持续转发成本。与此同时FirmFuzz从WebUI收集较有效请求，并加入内部异常和副作用监测。由此形成明确分工：执行底座负责每轮成本，输入生成负责请求能否进入处理逻辑，oracle负责异常能否被看见。FIRM-AFL §3–4、EQUAFL §3–5、§7、FirmFuzz §3。

关键认识：每秒执行更多输入，不能证明到达更多需要特殊状态的路径；EQUAFL本身也明确跨application和IPC建模边界。

6.3 从单个输入到消息序列：服务状态成为探索对象

AFLNet将响应状态与消息序列纳入反馈；固件方向的SIoTFuzzer保存多消息上下文，FirmHunter用状态队列和内省反馈分配测试预算，ESRFuzzer研究配置写入后再读取的消费路径。状态探索因此早于2024年，并不是LLM出现后才提出。通用StateAFL/SGFuzz则揭示另一问题：相同代码覆盖或响应码，可能对应不同内部状态历史。AFLNet §III、SIoTFuzzer §4–5、FirmHunter §3–4、ESRFuzzer Detailed design。

新增能力是“先建立有意义的前置状态，再变异目标操作”；尚未普遍解决的是未知接口、跨daemon、持久配置、异步任务和多协议共同状态。

6.4 从一个进程到完整服务：执行边界也决定漏洞可见性

Linux IoT中的一个外部请求可能触发httpd、短暂CGI、工具程序和后台daemon。Firmulti已提出全系统多进程异常观察（本轮仅摘要级）；HouseFuzz扩展服务级多进程反馈、test-case完成检测和token依赖；CGIFuzz将真实设备的调试插桩接入短暂CGI；STAFF用全系统动态污点和分阶段forkserver处理跨请求、跨服务依赖。内核方向FirmSolo/Pandawan又把原binary模块纳入动态测试。HouseFuzz §5–7、CGIFuzz §III、STAFF预印本 §4、§8、FirmSolo §3–4。

这些工作不能统称同一种“跨进程分析”：有的扩大异常监测边界，有的传播数据依赖，有的控制请求执行边界，有的恢复模块兼容性。CGIFuzz还需要先取得命令执行/调试和配置修改条件，不能写成无特权设备通用灰盒方案。

6.5 从广泛探索到验证具体候选：目标、输入约束和安全影响被连接

AFLGo给出位置distance驱动的通用方法；LABRADOR在黑盒设备上通过binary与响应字符串关联来近似目标进度；BullsEye尝试闭源固件basic-block distance。另一侧FirmRec将已知利用过程建成concolic signature，Bond把taint report还原为入口、字段和路径约束，再用定向变异寻找可重放证据。AFLGo §3–4、LABRADOR §3–4、BullsEye §5–6、Bond §3–5。

新增能力是把测试预算集中到候选漏洞；但“到达目标”“满足漏洞条件”“在仿真崩溃”“真机可重放”仍是不同证据。FirmRec模型内验证不是完整网络PoC，Bond未触发的报告中仍有可人工触发真漏洞，所以未验证应保持unresolved，而不是判作误报。FirmRec §5、Bond §4.2。

6.6 从语法知识到语义闭环：LLM被接入不同的确定任务

ChatAFL把协议先验用于grammar、seed与后续消息；mGPTFuzz从Matter规范提取测试信息；EAGLEYE恢复隐藏routing候选；PANGOLIN恢复跨语言参数层次并用响应纠错；FirmAgent从运行中发现输入源，用LLM进行语义污点分析，再回到PoC修订。Firmenstein则主要作用于环境干预。它们依靠的输入证据、工具与验收条件并不相同。ChatAFL §IV、EAGLEYE §III、PANGOLIN §3–5、FirmAgent §IV–VI。

真正需要比较的是：模型为哪一环引入了原先没有的有效信息，运行反馈如何否定错误推理，成本与人工干预是否下降。不能把使用某个新LLM、增加Agent角色或调用既有Fuzzer本身等同创新。

6.7 oracle与可复现性始终是贯穿问题

WYCINWYC早已说明memory corruption未必立即表现为可见crash。今天CGIFuzz、mGPTFuzz和Camveil仍分别研究非崩溃副作用与语义行为。另一侧Klees2018、SoK2024、IoTFuzzBench和LFwC说明：覆盖率、crash、确认漏洞、可执行目标数量是不同指标，实验设置可能改变比较结论。Fizzle把异步执行和输入完成边界的确定性作为网络Fuzzing机制，但对固件的适用性仍需检查。WYCINWYC §III–V、SoK2024 §5、Fizzle官方摘要。

反馈获取 只观察httpd，而真正危险动作发生在daemon Firmulti/HouseFuzz/STAFF
路径选择 已知疑似危险sink，但随机变异长期到不了 LABRADOR/Bond/BullsEye
漏洞判定 shell副作用没有使主服务崩溃 FirmFuzz/CGIFuzz类专用oracle；具体适用性另核
证明与复现 仿真stub改变了参数，或真机重放缺前置状态 FirmAgent/Bond及环境fidelity验证

这个例子说明，上述系统解决的是链条中不同位置的问题；表中的关联是机制类比，不声称某个系统已完整解决该示例。

D053 · STAFF（2026）

STAFF: Stateful Taint-Assisted Full-system Firmware Fuzzing

出处：Computers & Security 170 (2026), 105003；2025-09-22 arXiv v1。DOI：未核实。

适用对象：Linux/MIPS、HTTP管理工作流、多个daemon与多请求。

研究问题：跨daemon和持久状态依赖被单进程/单请求测试切断。

工程基础：FirmAE系统环境＋扩展DECAF++/QEMU的whole-system taint；对照系统移植AFLNet与TriforceAFL。

核心机制：人工交互录制请求序列、intra/inter-service taint hints、序列最小化、protocol-aware mutations、multi-staged forkserver。

新增能力/关系：把跨组件动态依赖实际用于主动序列变异和checkpoint，而非只报告跨binary静态流。

前提与局限：作者明确MIPS/HTTP范围、人工seed、重托管和taint近似/开销；正式版进一步说明instrumentation导致筛选/初始化失败。
